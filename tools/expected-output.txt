# Expected serial output for the documented commands.
#
# Read by tools/check-docs.ps1, which runs each command on a board and compares
# the result. The purpose is narrow: catch documentation that has drifted from
# what the firmware actually prints. A reader who sees one stale example has no
# reason to trust the rest.
#
# Format:
#
#   [command]
#   <regex>
#   <regex>
#   ...
#
# Each line is a pattern the captured output for that command must contain.
# Patterns are matched anywhere in the captured text, not line-anchored, so
# columns and surrounding chatter do not matter. Use `(?m)` anchors explicitly
# when a line position matters.
#
# Rules for what belongs here:
#
#   - Only output that the command itself prints. Not boot-time messages, not
#     the output of the selftest thread.
#   - Values are matched by shape, not by number: "tick     : \d+, \d+ Hz" not
#     "tick     : 35128, 1000 Hz". A number in a pattern is a test that fails
#     every run.
#   - Anything that legitimately varies (addresses, timings, RSSI) needs a
#     pattern loose enough to survive it but strict enough to catch a renamed
#     field.
#
# ORDER MATTERS. The checker runs sections top to bottom, in one boot.
#
# Three rules, each of which has already produced a false failure:
#
#  1. The `s3fsbench small` write and erase counts are exact, not a range.
#     They are 152/136 with use_one_fat = true, regardless of the volume's
#     history - measured across five states (just formatted, second run on the
#     same volume, after the bulk write, after a `s3fsbench write`, and across a
#     reboot with files left behind), the last three re-checked and identical.
#     190/170 means use_one_fat was turned off, and 1460 means the
#     allocation-unit tuning is missing. Exact values make both of those
#     visible; a range around 152 would only catch the first.
#
#     Creating 32 small files is sensitive to how spread out the directory
#     entries already are; the bulk write is too, but in time rather than in
#     write count. Measured on one board, one boot:
#
#       fresh volume                 -> 958 ms / 267 KB/s
#       fresh volume, after small    -> 2312 ms / 110 KB/s
#
#     Write counts are 79/71 in both cases - the extra time is the allocator
#     walking a fragmented free list, not writing more flash. Both benchmarks
#     want their own freshly formatted volume; a long sequence can only give one
#     of them that, so the ranges cover both states.
#
#  2. Anything timed runs before any radio starts. With Wi-Fi associated the
#     same s3fsbench write is 4567 ms / 56 KB/s instead of 1055 ms / 242 KB/s -
#     both correct, four times apart. A range that has to cover both is so wide
#     it catches nothing.
#
#  3. BLE comes before anything that initialises Wi-Fi. With Wi-Fi up the BLE
#     controller cannot get the ~56 KB of contiguous internal DRAM it needs and
#     fails with BLE_INIT: Malloc failed (docs/KNOWN-ISSUES.md section 12).
#
#  4. Reboot sections come last, and the checker enforces that itself.
#
#  5. Metadata lives in the block directly under a [section] header, before its
#     first pattern. Two key lines exist and both are read by check-docs.ps1:
#
#       # scope: U|B|E - what a failure there means (see below)
#       # order: after <section> | before <section>
#
#     The "before the first pattern" part is structural, not cosmetic. `# scope:`
#     and a sentence that happens to start "# apart:" are the same shape, and the
#     first version of the integrity check reported the i2cwatch prose as a key
#     called "apart". Only position distinguishes them.
#
#  6. The remaining order requirements are declared, not remembered. Each section
#     that has one carries a line directly under its header:
#
#       # order: after <section>
#       # order: before <section>
#
#     and check-docs.ps1 verifies them at parse time, before the board is touched.
#     A violation used to cost a full 40-minute run to discover - and was found
#     that way twice, once when `s3fs rm s3fs.txt` was placed ahead of
#     `s3fs read` and deleted the file that section checks for.
#
# Without rules 1 and 2 the s3fsbench ranges failed the first time the full
# sequence was run, reporting regressions that were really preconditions.
#
# Commands that depend on hardware not on this board (an I2C device, an SPI
# loopback jumper) assert only their "nothing found" branch, which is what a
# bare board prints.
#
# A line starting with "~" constrains a capture group of the pattern above it:
#
#   s3fsbench: create 32 small files -> (\d+) writes .*, (\d+) erases
#   ~ 1 in 145..200
#   ~ 2 in 136..136
#
# "N == VALUE" for values that are deterministic (write counts - they follow
# from the FAT and wear-levelling algorithms), "N in LO..HI" for values that are
# not (anything timed - SPI NOR erase time varies by 40% between runs on the
# same board).
#
# Every bound below comes from repeated measurement on this board, recorded in
# the section's own doc page. Do not widen one to make a test pass; find out why
# the number moved.
#
# ---------------------------------------------------------------- scope ------
#
# Every section carries a "# scope:" line saying what a failure there means. This
# port has only ever been run on one board, so "the assertion failed" and "your
# board is different" are not the same statement, and a reader on another board
# needs to be able to tell them apart without reading the source.
#
#   U - expected on any ESP32-S3
#       Kernel counters, scheduler behaviour, watchdog, BLE GATT handles, error
#       paths for missing files and missing leases. A failure here is a defect.
#
#   B - tied to this board's pins, partition or measured numbers
#       LED on GPIO48, I2C0 on GPIO8/9, the 1 MB storage partition, the exact
#       heap figures, the cycle and microsecond measurements. A failure here can
#       be a defect OR a different board; check the pin and the partition first.
#
#   E - depends on the environment
#       Whether an AP is in range, whether there is internet, whether a jumper
#       is fitted, what devices answer on the bus. A failure here is usually the
#       room, not the firmware.
#
# Counted: 17 U, 25 B, 8 E.
#
# The split is not a claim that the B sections are untrustworthy - they are the
# most informative ones on the board they were measured on. It is a claim about
# what a red result means, which is the question a new reader actually has.
